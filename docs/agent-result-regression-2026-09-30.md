算力任务卡保存的原始轮次进一步证明：模型已经给出过包含车次、天气/穿衣和地点的 Final。Agent 错误发送两次“地点未查询”的 Control 后，模型才开始重复 Action，并模拟 Observation。17:23:32 的算力日志显示该次请求以 `reason=stop` 正常完成。

## 根因与改动

1. **组合需求识别错误。** 拆分缺少“另外”等连接词；高铁识别不接受“早上9点左右”；天气识别不接受紧跟的穿衣问题。现在分别登记车次、天气、地点，避免生成跨问题的假地点。
2. **已执行结果匹配过严。** 没指定日期的天气需求误拒绝模型按出行上下文查询的明天；最终回答里的车站后缀、空格以及 `11°C`/`11.0°C` 也可能导致误判。现在允许未指定日期需求绑定单日结果，显式日期仍严格匹配；数值仍按完整 token 校验。
3. **模型继续模拟工具结果。** 1.1.53 真机回归发现，在需求识别修复后，模型仍可能在有效 Action 后输出 Observation，导致整批拒绝。1.1.54 在结构完整的 Action 之后识别工具结果边界，仅对 Registry 明确声明为只读、低风险的调用恢复执行。边界之后的所有模型文本及后续命令全部丢弃；历史只写入规范化的已校验 Action 和实际工具返回。未知工具、损坏 JSON、写操作、混合 Action/Final 不通过此兼容路径。
4. **汇总失败覆盖真实成功。** 格式异常/轮数耗尽时保留所有已执行结果，包括未被保守需求识别器绑定的结果，明确区分“综合回答未完成”和“工具查询失败”。

## 已取得的真机结果与后续修正

2026-10-08 读取保留的设备对话，确认 2026-09-30 的 1.1.54 原问题回归已经完成：最终回答包含车次、北京天气/穿衣及丽泽 SOHO 地址，原来的“工具调用格式未能修复”没有再次出现。该次保留了此前失败对话。

但该回答把全天车次列成了“9点左右”的车次，暴露了模型把 `左右` 从参数中丢失的问题。1.1.55 新增：

- 仅为一个明确匹配的路线、日期恢复用户原话中的时间窗；不修改其它路线、日期、工具、额外参数或 context。歧义路线不自动改写，未满足时间窗的调用不完成需求。
- 最终回答中路线标题下面的编号车次行也检查其代码是否来自本次工具结果，避免正文只校验标题而漏掉下面的全天车次。
- 后续模型调用失败或 prompt 超限时，已执行工具结果保留；主动停止仍不会发晚到 Final。
- `InferenceClient` 在请求发送异常和超时取消发送异常时都先结束本地等待并清理计时器，允许下一次调用。

连续请求暴露的进一步问题，已纳入最终版本：

- 单位工具原来支持 km/mi，但没有 km/m。新增公里与米的双向换算和溢出检查。
- 模型将旧天气、车次、地址混入新计算答案。当前任务提醒现在保留在提示词末尾，并计入强制 UTF-8 预算。明确点名的本地工具必须有真实调用；计算和单位转换答案的目标数值必须来自返回结果，额外数值只能来自本轮输入或结果。
- 窗口尺寸更新时执行记录的 collapsible 标记会被正文高度判断覆盖，导致标题仍显示但不能展开。现在执行记录始终保留展开能力。
- 当明确的计算/单位转换需求全部成功，而模型又重复同一组可缓存、低风险只读调用时，直接返回已验证结果，防止反复生成无新证据的调用。写操作不走此路径。
- 仅在提示词末尾重申任务仍不足以抵抗大量不相关历史。完整、独立的显式工具请求现在不向提示词或模型适配器传递旧对话；引用“上面、刚才、之前”等内容的追问仍保留上下文。持久化历史保留。
